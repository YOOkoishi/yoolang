## Goal

Close the current huffman-family performance gap against GCC `-O3` and Clang++ `-O3` with general, semantics-preserving compiler optimizations. The first target is to make the timed decode loop in huffman-like programs avoid expensive call boundaries, repeated global state loads/stores, table-load multiply/divide shift emulation, and overly long signed `% 2` predicate sequences.

## Non-goals

- Do not special-case huffman filenames, function names such as `read_bits`, `_or`, or `_and`, variable names, testcase identity, inputs, sizes, or expected output.
- Do not replace hand-written `_or`/`_and` loops with machine bitwise OR/AND unless a general range proof establishes equivalent signed semantics for all operands.
- Do not weaken perf scripts, correctness tests, runtime behavior, benchmark inputs, or output checks.
- Do not start broad OIR instruction-set expansion unless the smaller planned patches fail to expose the needed operations.

## IR And Assembly Observations

Generated diagnostics:

```bash
mkdir -p /tmp/huffman_analysis
build/linux/x86_64/release/compiler test/performance/huffman-01.sy --emit-oir -O1 > /tmp/huffman_analysis/huffman-01.yoolang.oir
clang++ -O3 -mcmodel=medany -std=gnu++17 --target=riscv64-linux-gnu --sysroot=/usr/riscv64-linux-gnu -include build/perf-ci/runtime/sylib_wrapper.hpp -x c++ build/perf-ci/test/performance/huffman-01/huffman-01.baseline.cc -S -emit-llvm -o /tmp/huffman_analysis/huffman-01.clang.ll
```

Key evidence:

- yoolang OIR inlines `decode_fixed_huffman` into `main`, but still has `call i32 @read_bits(i32 5)` inside the decode loop. Clang LLVM IR has the `read_bits(5)` logic expanded into `main`, which lets it keep `pos`, `bits`, and `buf` in SSA-like register state across the timed decode loop.
- yoolang final assembly calls `read_bits` for every decoded symbol in `main`; `read_bits` itself contains two 32-iteration inlined `_or`/`_and` loops and saves/restores nine callee-saved registers. Clang keeps the same signed arithmetic semantics but avoids the repeated call boundary in the hot decode loop.
- yoolang lowers `rotlN(data[pos], bits)` through a dense factor table load plus `mulw`, and `rotrN(buf, n)` through factor table load plus `divw`. Clang/GCC mostly use branch/jump-table cases with direct shifts for powers of two.
- yoolang signed `% 2 == 1` tests lower to longer div/rem-derived sequences. Clang keeps signed semantics but compacts the predicate with masks such as `and x, 0x80000001` followed by compare-to-one logic.
- Existing `MIRBitIdiomCombinePass` is local peephole only; it does not recognize source-level 32-iteration loops that compute bit predicates through signed `% 2` and `/ 2`.

## Invariants And Risks

Correctness invariants:

- All optimizations must preserve signed SysY/C integer division and remainder semantics, especially for negative operands.
- Constant-argument specialization must preserve call side effects and global memory behavior; it may only substitute scalar arguments, not assume globals are unchanged unless proven by existing analyses.
- Inlining/specialization must have code-size caps and site caps so it remains a general optimization, not a benchmark-specific expansion.
- Dense return-chain changes must only replace table multiply/divide with shifts when the power-of-two relationship and signed result equivalence are proven for the matched expression.

Contest / compliance constraints:

- Do not special-case filenames, function names, variable names, testcase identity, input sizes, input values, or expected outputs.
- Do not use huffman-specific source structure as a trigger; every patch must be justified by a general IR/MIR pattern.

Risk areas:

- Replacing `_or`/`_and` with machine bitwise ops is unsafe without range proof because the source uses signed `%` and `/`, not unsigned bit extraction.
- Raising global inline thresholds blindly may bloat code and regress other benchmarks.
- Clang uses both inlining and lower-cost signed remainder predicates; implementing only one may show a partial improvement.
- Perf reports under `build/perf-ci` are overwritten by each run; copy key numbers into this task after each focused run.

## Alternatives

| Option | Why considered | Decision |
| --- | --- | --- |
| Blindly raise inline thresholds | Would inline `read_bits` sooner | rejected as first step; high code-size and compile-time risk without call-site simplification |
| Recognize `_or`/`_and` by function name | Would directly collapse the benchmark helpers | forbidden; testcase/function-name special casing |
| Replace hand-written signed `%2` loops with bitwise OR/AND | Could be much faster | rejected unless range proof is added; negative signed operands differ |
| Add OIR `Or/Xor/Shl/Shr` immediately | Would make later transforms easier | deferred; first use existing `And` and MIR lowering capabilities for smaller, safer patches |
| Treat this as RA/PostRA problem | Final code is slower | rejected by metrics: `0` spills/stack slots and identical `pre-ra`/`post-ra` counts |
