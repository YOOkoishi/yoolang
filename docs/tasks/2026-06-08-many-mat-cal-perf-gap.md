Representative per-case codegen is identical across the three input points: final `232` MIR instructions, `83` moves, `27` jumps, `27` branches, `6` load opcodes, `5` store opcodes, `0` spills, `0` stack slots, `340` assembly lines.

Dominant loop:

- The matrix multiply inner loop runs about `T^3`, roughly 69 million iterations for these inputs.
- yoolang final assembly for `while.body.50` uses 8 steady-state instructions: two loads, two pointer bumps, one integer induction bump, `mulw`, `addw`, and `blt t3, s1`.
- Clang and GCC use pointer-end loop exits for the same hot loop. Clang's inner loop is 7 instructions (`lw`, `lw`, pointer bump, `mul`, `add`, strided pointer bump, `bne`); GCC's is also 7 steady-state instructions with `mulw/addw`.
- The extra integer induction update and compare in yoolang comes directly from OIR: `while.body.50` already has pointer phis for `C.1.addr.ptr` and `A.1.addr.ptr`, but the exit is still `%k.loop + 1 < %v0`. MIR lowers that shape faithfully.

Secondary gaps:

- The two timed `-1` fill loops are `O(T^2)` and smaller than matrix multiply, but GCC/Clang turn them into `memset(..., 255, T * 4)` calls. yoolang keeps scalar `sw -1` loops.
- The current OIR memset-style transform is specifically `lower_counted_zero_store_loops_to_memzero`; it matches only zero stores through `is_zero_store_value` / `single_zero_store`, so `-1` stores are outside its scope.
- The `val / 3` loop is not the primary issue: yoolang already lowers division by 3 to a magic-multiply sequence, similar in intent to GCC/Clang.

Attribution:

- Nearest responsible stage: `OIROptimizationPipelinePass`, specifically the OIR loop optimization/strength-reduction area.
- Primary concrete gap: `OIRLoopStrengthReductionPass::reduce_gep_strength` creates pointer induction phis for array accesses but does not rewrite counted loop exits to equivalent pointer-end comparisons or remove the now-extraneous integer induction. That leaves the backend with an extra hot-loop counter update and compare in the dominant matrix multiply loop.
- Secondary concrete gap: `OIRLoopTransforms::lower_counted_zero_store_loops_to_memzero` only handles zero-store loops. A general constant-byte-pattern store lowering would cover `int -1` fills without special-casing this benchmark.
- Rejected attribution: RA/PostRA/final ASM emission. There are no spills or stack slots, `pre-ra` and `post-ra` metrics are identical, and the final cleanup only removes moves/jumps. The poor hot-loop shape is already present before RA.

Recommended follow-up tasks:

1. Add a general OIR or MIR induction-compare elimination for counted loops whose pointer induction advances with the same trip count: materialize a pointer end in the preheader, branch on next/current pointer against that end, then DCE the integer IV if it has no other uses.
2. Add a general memset lowering for counted scalar stores whose stored value has a repeated byte representation, e.g. `0x00000000` and `0xffffffff`, with a non-zero memset representation instead of the current `MemZeroInst`-only path.
